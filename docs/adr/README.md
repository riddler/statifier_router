# Architecture Decision Records

| # | Decision | Status |
|---|---|---|
| [0001](0001-bindings.md) | A binding is host configuration with a fixed key set (`id`, `source`, `selector`, `match`, `key`, `document`, `event`, `data`, `create`, `dedupe`, `order`, `enabled`); `match` and `key` are predicator programs compiled once and evaluated over the adapter-normalized event; `match` holds only on exactly `true` and `:undefined` means not for this binding; a key that is not a non-empty string is a refusal recorded against the binding; one event reaches every binding whose match holds; `data` is a projection; `mode`, `batch` and `window` are reserved and refused by name | proposed |
| [0002](0002-addressing.md) | One table, the address, maps `(scope, document, key)` to an `execution_id`, unique on the triple; `document` is the stable document id, never a chart hash; `scope` is an opaque host string compared only for equality; the router mints an opaque execution id at create, never derived from the key, and the row records it; a host resolver answers which chart a new execution starts on; a finished execution keeps its row for the longest dedupe horizon of any enabled binding naming its document, counted from when the package first saw it terminal; `reap/2` is a plain function the host schedules; an `always_new` delivery writes no row | proposed |
| [0003](0003-delivery-discipline.md) | Each binding's delivery of an event is one transaction on the host's repo, holding the dedupe row, the address insert-or-lookup, `create/4` when the `create` mode calls for one, `step/5` and the ledger row; the input log is written only by statifier_persistence's `step/5`, never by the router; `step/5` runs inside the transaction, because stepping after the commit leaves committed deliveries unstepped with nothing to recover them, at the cost that effects fired before a rollback stay fired; the address insert, which inserts no row on a conflict, runs before `create/4`, so the loser of a race for a new key waits, reads the winner's row and never creates; `if_absent`, `never` and `always_new` are specified per address state; per-key serialization is `step/5`'s lock and a Broadway partitioner is an optimisation; dedupe is on `(binding_id, message_id)` with a row expiry of the binding's horizon, a structural message id for a queue source and the provider's event id or a hash of the verified body for a webhook; the router's dedupe and the engine's effect keys never merge; the scope rides with each event; the dedupe reaper is a plain function; `order: :none` is no partition | proposed |
| [0004](0004-the-refusal-and-drop-vocabulary.md) | One routing attempt produces exactly one outcome per enabled binding for the event's source: `delivered`, `created_and_delivered`, `duplicate`, `no_match`, `key_refused` (a refusing `match` or `key`, with the reason), `dropped: no_execution` or `dropped: finished`, each spelled as the tagged tuple `route/3` returns; delivered and created_and_delivered are recorded on the execution's input log and the binding's ledger, the others on the ledger only, and no_match on neither; for a refusal or a drop the router itself never creates, steps or writes an execution, except the create that precedes a dropped: finished (section 3); the ledger is `routing_ledger`, append-only; `route/3` returns `{:ok, outcomes}` in binding order or `{:error, reason}` for a failure that is not an outcome, which the front does not acknowledge; `dropped: unmatched_event` is out of this release | proposed |
| [0005](0005-routes.md) | The chart spells an outbound send as the host's processor in `type` with the route name in `target`, which the engine never parses and which never carries a host scheme; the route registry is per host, and a scope may override a route's config and never its existence, with nothing per execution; a route is one-way, returning `:ok | {:error, term()}` and no data, and the one event it can cause in the sender is `error.communication` with the send's `sendid`, which is transport failure and not an answer; a sink's result is a new inbound event through a binding, correlated by an author-written send `id` the adapter echoes, with the chart arming its own timeout as a delayed self-send; the idempotency key is composed by the router, from the effect's `send_id`, step counters, `c_index`, `owner` and `ordinal` plus `execution_id` at the executor seam or `session_id` on the send-processor shape, there being no `position` on either surface; one handler module serves both shapes, hands off durably inside the delivery transaction, never calls a door of the sending execution from `execute/2`, and on the process-less shape owns delayed sends and their cancel on the host's own timer queue keyed by `(scope, send_id)` - st-ADR-0054's cancellation key, never the send id alone, which recurs across executions - with decision 4's composed key beside the row as the separate dedup key; an unregistered route misses at lookup, is recorded as a refusal on the ledger, and its `{:error, _}` does not roll the step back | proposed |
| [0006](0006-the-execution-target.md) | A `<send>` of the host's registered processor type whose `target` is the reserved name `execution` and whose params carry `document`, `key` and an optional `create` resolves through ADR-0002's address table; the scope is the sender's, read from its own address row, never a param, so a chart cannot address another scope; resolution and delivery are ADR-0002's lookup and ADR-0003's one transaction, with the reserved name `execution` as the ledger row's `binding_id` and ADR-0005 section 4's idempotency key as its `message_id`, so a replayed step is a duplicate; `create` offers `if_absent` and `never` only, `always_new` being meaningless for an address; a miss under `never` and a terminal target under either mode are **reported to the sender as `error.communication` carrying the `sendid`**, through ADR-0005 section 7's two shapes, and the ledger row is a record of that report rather than a replacement for it, while `if_absent` has no miss to report; the delivered event is the engine's public builder's, with `origintype` the host's type and the three envelope params consumed; every refusal is a `send_refused` with a named reason, is reported to the sender by those same two shapes, and writes one ledger row - except the one reason discovered before the sender's scope is in hand, a sender with no address row, which the ledger's `NOT NULL` scope cannot record; a send to the sender's own address is one of the recorded reasons | proposed |
| [0007](0007-the-source-invoke.md) | A chart subscribes to a source only while it is in a state with `<invoke type="myapp:source">`, whose params name the binding id alone and never the key; the invocation's lifetime is the subscription's, so entering subscribes and the engine's own `{:cancel_invoke, _}` on state exit becomes `StatifierRouter.cancel/2` for that `(binding, execution)`; `cancel/2` undoes the subscription row it created and anything that subscription scheduled, nothing else; the cleanup table gives the invoke cancel to the host's invoke handler, a chart's own delayed send to the chart's `<cancel>` in `<onexit>`, and a registered send type's delayed send on a durable host to the send handler at the executor seam; durable executions only, with `mode` still a reserved binding key; a subscription is a new table, not an address row with a flag, and the code bead owns that migration alone | proposed |

New ADRs: next number, same three-section format (Context, Decision,
Consequences), each a new file `NNNN-<slug>.md` at `Status: proposed` with a
row in the table above. Pick the number against a freshly fetched remote. A
later change to a merged record is a Note or an Amendment appended at the
foot of the file; the body above it is not edited.

A bare `ADR-NNNN` cites this repository's own records; a cross-repo citation
carries the owning repo's beads prefix: `sp-ADR-NNNN` is statifier_persistence's
ADR-NNNN and `st-ADR-NNNN` is statifier-ex's.
